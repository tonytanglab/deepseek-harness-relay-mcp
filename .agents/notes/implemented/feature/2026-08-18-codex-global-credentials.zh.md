# Agent Note: Codex 全局凭据与项目覆盖

Status: implemented

[English](2026-08-18-codex-global-credentials.md) | 中文

## 问题

Codex MCP 监管器为每个规范化工作区分配独立的 Harness home，避免会话、设置、附件和索引相互冲突。这项隔离也把 `.credentials.yaml` 放进了工作区哈希目录，导致从一个项目的 Models 页存储的密钥在其他项目中不可用，并且轮换密钥时必须逐个修改服务 home。

## 决策

监管器保留工作区专属的 `DSH_HOME`，并通过 `DSH_GLOBAL_CREDENTIALS_PATH` 单独传递一条用户级全局凭据绝对路径。基础组合包把这个可信进程值映射为 `dsh-credentials-local.globalPath`，并且只为受监管子进程选择 `global` 作为默认写入作用域。未携带该值的 Harness 直接启动继续使用单一项目文档，并保持原有 API 结果。

本地提供方依次解析继承的进程环境、项目受管文档、可选全局受管文档、项目 `.env` 和用户 `.env`。两份受管文档都保留仅属主校验、原子写入、跨进程锁、热重载和明确失败的解析行为。凭据 Service Definition 和 Host RPC 接受可选的 `global` 或 `project` 写入作用域；仅当提供方拥有两份文档时，`describe()` 才公开作用域元数据。

Models 编辑器只在两个作用域均可用时渲染作用域选择框。已配置的密钥从当前生效的受管作用域开始，未配置的密钥从提供方默认值开始。把项目覆盖切换为全局时，系统会先写入全局文档，提交成功后才移除项目条目。项目文件仍是优先级更高的显式覆盖。删除提供方 profile 时绝不删除用户级全局凭据，因为其他工作区可能仍在使用它。

## 考虑过的替代方案

**把凭据文件复制到每个工作区 home。** 这能保持旧提供方不变，但会复制机密，使跨项目轮换不具备原子性，并留下继续遮蔽新值的陈旧副本。

**让所有 Codex 项目共用一个 `DSH_HOME`。** 这会共享密钥，却也会合并会话、设置、附件和索引，违反监管器的隔离所有权规则。

**把共享密钥放入每个子进程的环境。** 这会让 Models 页无法写入该值，并把受管机密物化到进程环境中，违背凭据提供方的存储规则。

## 测试

提供方测试固定优先级、分作用域写入、未指明作用域时的全局默认、非法路径配置、全局热重载和不变的单文档行为。Host 测试固定不返回值的 wire 作用域转发；Client 测试固定选择框默认值、「先写全局、再移除项目」顺序，以及删除提供方 profile 时保留共享凭据；MCP 测试固定全局路径向子进程的显式传递。类型检查和构建覆盖生成后的 Host/Client 约定及已安装 CLI 产物。

## 后果

全局存储的密钥会立即供所有新启动或已监视的 Codex 工作区服务使用，而有意设置的项目凭据仍在本地优先。既有工作区凭据文件继续有效并充当覆盖；在该工作区选择全局会迁移选定引用，且不会在共享值持久化之前删除覆盖。全局文件与项目文件具有相同的文件权限限制：以同一用户运行的模型工具进程只要刻意发现路径就能读取，因此需要更强隔离时仍应采用 OS 钥匙串提供方。
